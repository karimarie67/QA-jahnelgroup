# QA-jahnelgroup

Automated QA for the Jahnel Group website, https://www.jahnelgroup.com:
Playwright tests of its pages, menus, contact form, open roles, links, and
accessibility, on a desktop browser (Chromium, 1280×720) and an emulated
phone (Pixel 5). The repo was created from the
[`QA-framework-template`](https://github.com/karimarie67/QA-framework-template)
Framework. Its scope is in the [Engagement brief](./docs/engagement-brief.md),
and how it was built, step by step, is in the
[Engagement log](./docs/engagement-log.md).

## Where things stand

- **User stories and test cases.** Six user stories, each with its test cases
  as sub-issues, and every test case automated by one Playwright test. The
  stories are QA-drafted, pending agreement with the client contact. See the
  [coverage map](./docs/coverage-map.md) for which test covers which case, and
  the [`user-story`](https://github.com/karimarie67/QA-jahnelgroup/issues?q=label%3Auser-story)
  and [`test-case`](https://github.com/karimarie67/QA-jahnelgroup/issues?q=label%3Atest-case)
  issues for the stories and cases themselves.
- **Known defects.** The site's open defects are the
  [`qa` issues](https://github.com/karimarie67/QA-jahnelgroup/issues?q=is%3Aopen+label%3Aqa).
  Each is caught by a test, which names it.
- **Red on purpose.** A test that fails on a known site defect is left
  failing, so its CI check stays red until the site is fixed. That's the
  honest result, and the choice is recorded in the log (step 7). Today the
  Smoke, Error Handling, and Functional checks are red, on the four `qa`
  defects and nothing else. Any other red check is new.

## The rules the tests keep

The site is live, and there's no staging copy, so every test is
**read-only**. The full rule is in the brief's Environments table.

- **Load and look.** Tests navigate, read the page, and open and close menus,
  filters, and dialogs.
- **Never type into or submit a form**, not even an empty one. The contact
  form sends real mail, and Apply sends a real application to Greenhouse.
- **Go gently.** One worker at a time, no load or stress runs, and the link
  checker on demand only.

## Running the tests

```bash
npm install
npx playwright install chromium

npx playwright test --grep @smoke --project=production --project=production-mobile        # smoke suite, desktop and phone
npx playwright test --grep @regression --project=production --project=production-mobile   # error handling, content, and accessibility
npx playwright test --grep @a11y --project=production         # any tag, e.g. the accessibility tests on desktop
npm run test:links           # link checker (the link-checker project; crawls the whole site)
npm run test:unit            # unit tests
npm run test:template-check  # checks the config imports, every spec is discovered, and every test's tags fit
npm run lint                 # ESLint, with the Playwright plugin for the specs
npm run coverage             # regenerates docs/coverage-map.md
```

`staging` and `production` both point at the live site, as do their `-mobile`
phone projects, so run one environment at a time (the npm `test:smoke` and
`test:regression` scripts use `staging`). Tests run one at a time
(`workers: 1`). Local runs rewrite `dashboards/`, which CI owns: don't commit
those changes.

**What CI runs, and when** ([`qa-test.yml`](./.github/workflows/qa-test.yml)):

| When | What runs |
|---|---|
| Every push and PR to `main` | Smoke (`@smoke`) and Functional (`@regression`: error handling, content, and accessibility) tests, on desktop and phone; lint; unit tests; the template check, including the tags and that the coverage map is current |
| After a push to `main`, and after a manual run | The dashboard updates, and CI commits it to `main` |
| A manual run of the workflow | Pick `smoke`, `regression`, `links`, or `all`. The link checker runs only this way. |

## Going forward

- **Triage.** New `qa` issues arrive with `needs-triage` and a proposed
  severity from the brief's examples. Confirm or change it, remove
  `needs-triage`, and move the issue on the board.
- **A red test turns green.** The site fixed a known defect. Re-check it on
  the live site, close its `qa` issue, and remove the
  "Fails on the live site today: known defect #N" comment from the test.
- **A new defect.** A red check that isn't a known defect is new. Re-check it
  on desktop and phone, then file it with the QA Finding form (`qa`,
  `needs-triage`), add it to the board, and add or extend a test that catches
  it, with the comment naming the issue.
- **An intended site change.** A new page, a renamed menu item, or new copy
  turns a test red for the right reason. Probe the page read-only, update the
  expected values in `config-helper.js` (and `selectors.js` if an element
  changed), and update the test case issue to match. For a new page, also add
  it to `urlPatterns` and `testData.pageTitles`.
