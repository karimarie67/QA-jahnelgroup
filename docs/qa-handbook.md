# QA Handbook

How QA works in every Engagement built from this Framework. It is written
once, here, and every Engagement inherits it through "Use this template".

This handbook deliberately leaves two kinds of content out:

- **Engagement specifics** (what is under test, environments, release gates,
  severity rules agreed with the client, contacts, access) go in that
  Engagement's [`docs/engagement-brief.md`](./engagement-brief-template.md).
  Fill it in at kickoff; it is the only per-Engagement document to write.
- **Facts the repo already states** (test counts, which specs exist, what CI
  runs, pass rates) are not restated here. Read them from their source, which
  is always current:

| Question | Source |
|---|---|
| Which test cases are automated, and where? | [`docs/coverage-map.md`](./coverage-map.md), generated by `npm run coverage` |
| What do the tests cover, and what's still manual? | `test-case` issues, grouped under their `user-story` issues |
| What runs in CI, and when? | [`.github/workflows/qa-test.yml`](../.github/workflows/qa-test.yml) |
| Current and recent pass rates | [`dashboards/qa-metrics.md`](../dashboards/qa-metrics.md) |
| Commands, and what counts as proof of work | [`docs/agents/testing.md`](./agents/testing.md) |
| How to run the tests day to day | [`README.md`](../README.md) |

The original Boost.org handbook this was extracted from is kept in the
repository's history:
[`examples/boost/QA_handbook.md`](https://github.com/karimarie67/QA-framework-template/blob/76f455d/examples/boost/QA_handbook.md).

## 1. The QA chain

Every piece of QA work traces through the same chain:

```
user story ──► test case(s) ──► automated test ──► CI run ──► dashboard
 (issue)       (sub-issues)      (one per case)
```

1. **User story**: a GitHub issue created from the **User Story** form
   ([`.github/ISSUE_TEMPLATE/user-story.yml`](../.github/ISSUE_TEMPLATE/user-story.yml)),
   labeled `user-story`, that states a behavior and numbers its acceptance
   criteria (AC).
2. **Test case**: a GitHub issue created from the **Test Case** form
   ([`.github/ISSUE_TEMPLATE/test-case.yml`](../.github/ISSUE_TEMPLATE/test-case.yml)),
   labeled `test-case`. It names its source story and the ACs it covers, and
   is added as a **sub-issue** of that story, so the story shows its test-case
   progress. Every AC is covered by at least one case.
3. **Automated test**: one Playwright test per test case. It declares the
   case's ID (and its issue) as annotations, so the coverage map and the
   dashboard can trace it back.
4. **CI and dashboard**: the workflow runs the tests and publishes results
   to `dashboards/qa-metrics.md`.

A client that tracks work in Jira keeps the same chain, with the stories,
test cases, and bugs in Jira: see [`jira.md`](./jira.md).

### Test case IDs

```
TC_<AREA>_<NNN>     e.g. TC_SMOKE_001, TC_A11Y_001, TC_CART_002
```

`<AREA>` is a short, stable name for the feature or suite; `<NNN>` is the next
free number in that area (check `docs/coverage-map.md`). An ID is never reused,
even after its test case is closed.

### Test case status

A test case stays open as a living record. Its label tracks automation:

| Label | Meaning |
|---|---|
| `test-manual` | Executed by hand; not automated |
| `test-needs-automation` | Approved for automation, or automation is in an open PR |
| `test-automated` | Automated and merged; *Automation File Path* names the spec and test |

## 2. Testing strategy

**Shift left**: run fast checks as early as possible and the full suite
before anything reaches production.

| Stage | What runs | Why |
|---|---|---|
| Pull request | Smoke tests, unit tests, `template-check`, lint | A fast gate before code merges |
| After merge | The full suite | Validates the integrated change |
| Before a release | The full suite against the release candidate environment | Release gate (the brief sets the threshold) |
| After a release | Smoke tests against production | Confirms the release, within the limits the brief allows for production |

The workflow implements this. The template ships with browser e2e jobs on
manual dispatch only, until an Engagement replaces the placeholder Site
config, and the Engagement then enables them on push and PR. The brief records
the Engagement's actual choice, including any scheduled monitoring.

**Smoke tests** are the few tests that prove the critical paths work: the
ones tagged `@smoke` (`npx playwright test --grep @smoke`). Keep the set
small enough to finish in minutes.

**API tests** check what the site's own API answers, without a browser:
`tests/api_tests.spec.js` reads each endpoint in `siteConfig.api` (GET only)
and checks its status, content type, and the JSON fields it promises. Tagged
`@regression` and `@api`.

**Performance budgets**: `tests/performance_tests.spec.js` measures each
page's Web Vitals (LCP, CLS, TTFB, load time) in Chromium during a normal load
and fails a page over the budgets the brief sets (`siteConfig.perf`). The
numbers are attached to each run's report. Tagged `@regression` and `@perf`.

**Visual checks**: `tests/visual_tests.spec.js` compares each page's
screenshot with a committed baseline (`siteConfig.visual`). Screenshots differ
by operating system, so it runs only in Playwright's Docker image: `npm run
test:visual` to compare, `npm run test:visual:update` to make or refresh the
baselines, which are reviewed and committed like code. Tagged `@regression`
and `@visual`; it skips in any other run.

**Other browsers**: the projects run Chromium on desktop and a Pixel 5
emulation. When the brief asks, `QA_BROWSERS` adds Firefox, WebKit (Safari's
engine), and an iPhone emulation for the public specs (see
`site-config.md`, "Phones").

**Manual testing** stays manual when a script can't judge it well:
exploratory sessions, visual review, accessibility with assistive technology,
and one-off checks. Each lasting manual check is still a test case, labeled
`test-manual`.

**A suite that catches real defects.** Some practice sites offer accounts or
variants that are broken on purpose (Sauce Demo's `problem_user`, say). Running
the suite as one of those, or giving a test case of its own to the broken
variant, shows the tests fail when the site is wrong, which no green run can.
Its failures are expected, so keep it off the dashboard and out of the push
and PR gate.

### Recording a manual run

Comment on the test case issue:

```
Manual run — <date>, <environment>, <browser/device>
Result: PASS | FAIL | BLOCKED
Notes: <anything unexpected; link a bug if FAIL>
```

`BLOCKED` means the case could not be executed, for example because the
environment was down. It is never a pass.

## 3. Bugs

### What is a bug

A bug is observable behavior that contradicts an acceptance criterion, the
site's documented behavior, or basic function: a broken link, a page that
won't load, an action that fails, an error that stops the user.

A suggestion ("this could be faster", "this could look better", "add X") is an
**enhancement**. File it with the feature request form.

### Reporting

1. **Reproduce it**, in the lowest environment the brief allows (usually
   staging), and note whether production is affected too.
2. **File it** with the **Bug Report** form (or **QA Finding** for findings
   from a test session). Include steps to reproduce, expected and actual
   behavior, environment, browser, and a screenshot or video.
3. **Set severity** with the form's scale:

   | Severity | Meaning |
   |---|---|
   | Critical | Blocks all testing or usage |
   | High | Major functionality broken |
   | Medium | Feature partially broken; a workaround exists |
   | Low | Minor or cosmetic |

   The brief may add Engagement-specific examples for each level. It does not
   redefine the scale.
4. **Link it**: reference the failing test case (`TC_…`) and, if automation
   caught it, the CI run.

### Triage

On the cadence the brief sets (weekly by default), review open bugs, failed
runs, and dashboard trends. Confirm severity, close bugs verified fixed in
the environment where the fix lands (production, when there's no staging), and
raise anything urgent with the development team.

### When an automated test fails

Decide which of these it is before doing anything else:

| Cause | Action |
|---|---|
| A real defect | File a bug, link the run, and block the PR or release if severity warrants it |
| The site changed on purpose | Update the selector or expectation in the same PR as the change, or right after it |
| A flaky test | Fix the test (see [Flaky tests](#flaky-tests)); don't just rerun until it's green |

## 4. Writing an automated test

### Before you start

- Start from a test case issue. If there isn't one, write it first: steps
  and expected results are the test's specification.
- Check [`docs/coverage-map.md`](./coverage-map.md) for an existing test to
  extend.
- Decide whether it is a smoke test.

### Where things go

| What | Where |
|---|---|
| URLs, the site's pages, menu, and forms, and test data | `config-helper.js` (`buildURL`, `siteConfig`, `testData`) |
| Element selectors | `selectors.js` (`selectors.<name>(page)`) |
| Reusable flows | `test-helpers.js` (`testPatterns`, `testElementVisibility`, …) |
| Base URLs per environment | `playwright.config.js` projects (`staging`, `production`, …) |
| The test | The spec for its area under `tests/` |
| A test that needs a login | A spec named `*.auth.spec.js`: only the `-auth` projects run it, from the session `tests/auth.setup.js` saves (`siteConfig.auth`). No screenshots or evidence captures in it: a logged-in page can show the account's data |

### Anatomy

```javascript
import { test, expect } from '@playwright/test';
import { selectors } from '../selectors.js';
import { buildURL } from '../config-helper.js';

test.describe('Pricing Tests', { tag: ['@regression', '@pricing'] }, () => {
  test('TC_PRICING_001 The pricing page lists the three plans', {
    annotation: [
      { type: 'test_case', description: 'TC_PRICING_001' },
      { type: 'issue', description: 'https://github.com/<org>/<repo>/issues/42' },
    ],
  }, async ({ page }, testInfo) => {
    // Arrange: build the URL from the project's baseURL, never hard-code it
    await page.goto(buildURL(testInfo, '/pricing'));

    // Assert: web-first assertions wait for the condition by themselves
    await expect(selectors.site.mainHeading(page)).toHaveText('Pricing');
    await expect(page.getByRole('heading', { level: 2 })).toHaveCount(3);
  });
});
```

Conventions:

- **Put the ID first in the title.** It makes `-g TC_PRICING_001` work and
  puts the ID on the dashboard, which shows test titles.
- **Give every test one suite tag**, usually on its `describe`: `@smoke`
  (the few critical-path checks), `@regression` (everything else that runs in
  CI), or `@links` (the link checker only). CI selects by suite tag, so a new
  spec runs with no workflow edit. Add area tags as useful (`@a11y`,
  `@forms`, `@pricing`), never one that starts with a suite tag's name
  (`@smoke-visual`), and never put a suite tag in a title or file name:
  `--grep` would match it. A logged-in spec (`*.auth.spec.js`) is
  `@regression`. `template-check` enforces all of this.
- **Run by tag**: `npx playwright test --grep @a11y --project=staging`, or
  `--grep-invert @smoke` for everything but.
- **Declare annotations in the test's details object**, as above. Annotations
  pushed at runtime (`testInfo.annotations.push`) are invisible to
  `playwright test --list`, so the coverage map can't see them.
- **One test case per test.** If a case has sub-scenarios, use `test.step()`
  inside the one test.
- **Add a `client_case` annotation when a test traces to a client's own test
  case.** Declare it in the details object next to `test_case` and `issue`,
  with the client's own ID as its description. `npm run coverage` shows it in
  the Client case column. A test covering several client cases gets one
  `client_case` annotation per case.

### Step by step

1. **Find selectors.** Run `npx playwright codegen <staging URL>` and click
   through the flow. Prefer role, label, or test-id locators over CSS paths.
2. **Add them to `selectors.js`**, next to the existing entries.
3. **Write the test** in the right spec, following the anatomy above.
4. **Run it**:
   ```bash
   npx playwright test -g "TC_PRICING_001" --project=staging
   npx playwright test -g "TC_PRICING_001" --project=staging --headed   # watch it
   npx playwright test -g "TC_PRICING_001" --project=staging --debug    # step through it
   ```
5. **Check that it can fail.** Break the expectation briefly and confirm the
   test goes red, then restore it.
6. **Regenerate the coverage map**: `npm run coverage`.
7. **Lint it**: `npm run lint` (`npx eslint --fix` fixes what it can). It
   catches a missing `await` on an assertion, a stray `test.only`, and unused
   or undefined names; it doesn't catch a missing `await` on an action such
   as `page.goto`.
8. **Open a PR** that references the test case issue, and fill in the PR
   template (`.github/pull_request_template.md`): what and why, the test
   cases, the evidence path, and its checklist. Once it merges, label
   the case `test-automated` and fill in *Automation File Path*.

### Best practices

**Do**

- Use web-first assertions (`await expect(locator).toBeVisible()`). They
  retry until the condition holds.
- Keep tests independent. Each test sets up its own state and never relies on
  another test having run.
- Keep URLs in `config-helper.js` and selectors in `selectors.js`.
- Clean up any data a test creates, or use data the site resets itself.

**Don't**

- Hard-code URLs (`page.goto('https://…')`). Use `buildURL` or a relative path
  against the project's `baseURL`.
- Use `page.waitForTimeout()` as a fix for timing. Wait for the condition
  instead.
- Commit credentials. Real secrets go in CI secrets (the Atlas guard also
  refuses them in files an agent writes). For a public demo account, read the
  credential from where the site publishes it rather than copying it in.
- Skip a test without an issue that says why.

## 5. Keeping tests healthy

### When the site changes on purpose

1. Run the suite to see which tests fail, and read each error.
2. Find the new selector with `npx playwright codegen`.
3. Update `selectors.js` (or the expectation in `config-helper.js`).
4. Rerun the affected tests, and say in the commit message what changed on
   the site.

### Flaky tests

A flaky test passes and fails without any change. Common causes:

| Cause | Fix |
|---|---|
| Asserting before the element is ready | Use a web-first assertion instead of reading state immediately |
| Waiting on a network the site keeps busy | Wait for the element or response you need, not `networkidle` |
| Animation or transition | Assert the end state; Playwright's actionability checks wait for stable elements |
| Hidden duplicate of an element | Filter to what a user sees: `locator.filter({ visible: true })` |
| Bandwidth-heavy steps in parallel (large downloads) | Run those tests serially, or give them their own timeout |
| A control a site builder wires up after `load` (Wix, Squarespace) | A click before then does nothing. Retry the action until its result shows: `expect(async () => { … }).toPass()` |
| A closed slide-in menu that's off-screen | Playwright counts it as visible. Check `toBeInViewport` for "open" |
| A live site rate-limiting the run (HTTP 429) | Lower `workers`, space requests with `politeGet`, and run request-only checks once, on desktop |

In CI, the test runner retries a failed test once (`retries` in
`playwright.config.js`); locally it doesn't, so a flaky test shows up while
you're writing it. A test that passes only on retry is reported as flaky on the
run's HTML report and the dashboard; fix it rather than relying on the retry.

### Troubleshooting

| Symptom | Try |
|---|---|
| Fails locally, passes in CI | `npm ci` and `npx playwright install` to match CI's versions; run with `CI=true` |
| Element not found | Regenerate the selector with codegen; check that it isn't inside a hidden block |
| CI didn't run | Check the workflow's `on:` triggers and job `if:` conditions, and that Actions is enabled for the repo |
| Dashboard didn't update | The dashboard job runs only on the events its `if:` allows; check the run's *Update QA Dashboard* job |

## 6. Proof of work

When a change claims a test passes, the proof is committed under
`test-results/` on the branch and linked from the PR. It is never described as
"attached" if it only exists on someone's machine. The full rules (clearing
the evidence folder, one folder per test, when a screenshot or video is
needed, scrubbing sensitive data) are in
[`docs/agents/testing.md`](./agents/testing.md).

## 7. Routine

**Daily** (about 10 minutes)

- Check the latest workflow runs for failures, including the nightly
  scheduled run once the Engagement has turned it on.
- Check the dashboard for new failures or a falling pass rate.
- Check open Critical and High bugs.

**Weekly**

- Triage bugs and new test cases.
- Look for flaky tests in recent runs and fix the worst one.
- Run `npm run coverage` and review stories whose ACs lack a test case.

**Monthly**

- Review Dependabot's update PRs, Playwright's above all (run the full suite,
  and the logged-in no-leak check its comments describe, before merging).
- Review the slowest tests.
- Reread the engagement brief with the client contact and update anything
  that changed.

## 8. Keeping this handbook accurate

Change this handbook when the Framework's process changes, in the template
repo, by PR. Engagements pick up changes by copying the new version in.

Before adding anything, ask whether it is:

- **The same for every Engagement?** It belongs here.
- **Specific to one Engagement?** It belongs in that Engagement's brief.
- **A fact the repo already states** (a count, a list of specs, a schedule, a
  pass rate)? Link to the source instead of copying it.
